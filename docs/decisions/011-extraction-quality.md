# 011. 마감 추출이 맞는지 어떻게 재나

**상황.** 마감 추출은 정규식 규칙이고, 그림 공지는 AI가 받아 적은 글을 같은 규칙에 넣는다. 2026-10-29에 그림 공지 18건을 시험하다 규칙 오류 여섯 가지가 나왔고, 모두 글 공지에서도 생길 수 있는 것이었다. 고칠 때마다 다른 공지가 깨지지 않았는지는 그때그때 손으로 비교했다. 실사용자가 없어서 사용자 신고로 오류를 알 길도 없다.

**선택지.** (1) 지금처럼 고칠 때마다 손으로 비교한다. (2) 정답셋을 만들고 규칙이 바뀔 때마다 CI에서 같은 공지를 다시 돌려 정밀도와 재현율을 잰다. (3) LLM에게 결과가 맞는지 판정시킨다.

**결정.** (2). 저장해 둔 공지 89건(글 71건, 그림 18건)의 본문과 받아 적은 글을 테스트 자료로 넣고, 공지마다 학생이 할 일의 마감일(ACTION 종료일)을 정답으로 붙였다. `ExtractionBacktestTest`가 앱과 같은 코드로 마감을 뽑아 정답과 비교하고, 정밀도나 재현율이 `baseline.json`보다 떨어지면 실패한다. 수치가 오르면 baseline을 올린다. 그림은 다시 받아 적지 않으므로 이 테스트에는 API 비용이 없다. 운영 중에는 검수 기록(`review_event`)이 같은 지표의 실사용판이 된다.

**정답을 만든 방법.** 글 공지는 추출기 결과를 보지 않는 별도 에이전트 셋이 원문만 읽고 라벨을 붙였다. 그림 공지는 그림을 직접 보고 만든 정답지를 썼다. 추출기와 라벨이 엇갈린 13건은 원문을 다시 보고 판정했다. 라벨이 틀린 건은 없었고, 판정 결과는 `labels.json`의 known에 오류 유형으로 남겼다. 사람이 전부를 다시 확인하지는 않았다.

**처음 잰 값 (2026-10-30).** 공지 89건, 마감 89개에서 정밀도 0.886, 재현율 0.886이었다. 글 공지는 0.868/0.868, 그림 공지는 1.000/1.000이다. 그림 공지 18건은 규칙을 고칠 때 본 자료라 점수가 후하게 나온다. 어긋난 20개는 모두 규칙 쪽이었고 라벨이 틀린 것은 없었다. 유형은 여덟 가지로 나눴다. 행사·근무 기간을 마감으로 읽음 7, 두 자리 연도 4, 표가 있으면 문단을 안 읽음 2, 문장 속 마감 2, 과목조회 날짜 2, 제목 태그 라벨 1, 시작일만 있음 1, 한 칸의 마감 둘을 합침 1이다. 어긋난 날짜는 모두 `labels.json`의 known에 유형으로 적어 두었고, 분류되지 않은 새 오류가 생기거나 고친 오류가 known에 남아 있으면 테스트가 실패한다.

**고친 뒤 (같은 날).** 백테스트를 보며 유형별로 고쳐 정밀도 0.977, 재현율 0.977이 됐다(글 공지 0.973/0.973). 두 자리 연도("`26.10.19"), 제목 태그 라벨, "부터"나 물결만 있는 시작일, 운영·근무·진행 기간과 특강, 과목조회, 한 칸의 끝 날짜 여럿을 고쳤고, 표가 있어도 "모집기간"처럼 뜻이 분명한 기간 줄은 문단에서 읽게 했다. 고치는 중에 테스트가 두 번 막았다. 하나는 "까지 학점교류"의 "학점"을 수치 꼬리로 보고 마감을 버리던 숨은 버그였다. 다른 하나는 라벨러 사이에 갈린 기준으로, 추천채용 공지의 서류전형 종료일을 마감으로 볼지가 2대2였다. 서류전형은 회사의 전형 단계라 마감으로 보지 않기로 통일했다. 수강신청 공지에서는 문단에만 적혀 있던 복학 신청 기간을 새로 찾았다. 남은 오류는 문장 속 마감 2개("10월 3일 오전까지 보내 주세요")와 특강 일정표 2개다. 이 숫자는 고칠 때 본 자료로 잰 것이라 새 공지에서는 더 낮을 수 있다. 새로 모이는 공지로 정답셋을 늘려 다시 잰다.

**이유.** (1)은 바꿀 때마다 빠뜨리기 쉽고 수치가 남지 않는다. (3)은 판정하는 쪽도 틀릴 수 있어 정답이 흔들린다. 마감일은 맞고 틀림이 분명한 값이라 정답셋으로 재기에 알맞다.

**면접에서 한 문장.** "정규식과 AI가 섞인 마감 추출을 정답셋 89건으로 CI에서 재고, 정밀도나 재현율이 떨어지면 빌드가 깨지게 했습니다."
